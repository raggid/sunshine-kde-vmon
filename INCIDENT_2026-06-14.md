# Incident Log — 2026-06-14

## What We Were Trying to Fix

The Moonlight stream would time out immediately after connecting — no video, no audio. Investigating this led to the root cause described below (PipeWire session teardown), and the fix applied to the start scripts. **Applying that fix and restarting services to test it caused the second incident (Display Recovery Failure) documented at the bottom of this file.**

---

## Stream Timeout (root cause found and fixed)

### Symptom
Moonlight connected, prep-cmds ran successfully, Steam Big Picture launched — but the video stream never started. TCP control port (47984) was established; no UDP video/audio packets flowed. Moonlight timed out.

### Root Cause
Sunshine opens the KWin screencast (PipeWire session) **before** the prep-cmd runs, locking in the vmon's current resolution. The start scripts then called `kscreen-doctor output.<vmon>.mode.<RES>@<FPS>` to resize the vmon to the client's requested resolution. KWin tears down the screencast when the output reconfigures, PipeWire goes dead, and no video frames ever arrive.

Evidence:
- `sunshine.log` and `journalctl` both end at `Executing Do Cmd: [setsid steam steam://open/bigpicture]` — no further Sunshine activity
- `pw-cli info 168` showed the previously logged PipeWire screencast node was gone (taken over by Steam audio)
- `pw-cli list-objects` found no screencasting nodes
- `ss -unp` showed no UDP connections despite the TCP control link being established

### Fix Applied
Removed `output.${VMON_OUTPUT}.mode.${RES}@${FPS}` from both start scripts. The vmon now keeps whatever resolution the service created it at throughout the stream. Sunshine captures at that resolution and scales to the client's negotiated resolution.

Files changed:
- `vmon/sunshine-start-exclusive.sh` — removed `apply_custom_mode` call and mode argument from kscreen-doctor
- `vmon/sunshine-start-vmon.sh` — same

### Recommendation
To avoid scaling, set the vmon to the client's expected resolution ahead of time via service override:

```
~/.config/systemd/user/sunshine-vmon.service.d/override.conf
[Service]
Environment=SUNSHINE_VMON_WIDTH=2400
Environment=SUNSHINE_VMON_HEIGHT=1080
```

## Display Recovery Failure After Restart (unresolved)

### What Happened
After the fix was applied, both services were restarted simultaneously with:
```
systemctl --user restart sunshine-vmon.service sunshine.service
```

The previous stream session had used exclusive mode, which disabled DP-1 (physical monitor). The stop script (`sunshine-stop-vmon.sh`) had already been failing to re-enable DP-1 before the restart (logged errors). After the restart, KDE was left with both outputs disabled and in a corrupted replication state.

### KDE Display State After Restart
```
Output: DP-1       — disabled, replication source: 2, pos: 0,0
Output: Virtual-sunshine-vmon — disabled, replication source: 2, pos: 0,0
```
(Virtual-sunshine-vmon mirroring itself — circular replication)

### Errors Encountered
- `kscreen-doctor output.DP-1.enable` → `Position of enabled output DP-1 is negative (-2147483647, -2147483647)`
- `kscreen-doctor output.DP-1.position.0,0` → `Não é permitido desabilitar todas as saídas` (no other output active)
- `kscreen-doctor output.Virtual-sunshine-vmon.enable` → `An output cannot mirror itself`
- After killing vmon/krfb: `kscreen-doctor output.DP-1.enable` → `O driver rejeitou a configuração de saída` (NVIDIA driver rejected)

### Steps Tried (none succeeded)
1. `kscreen-doctor output.DP-1.enable position.0,0 priority.1` — negative position error
2. Set vmon position first, then enable DP-1 separately — same error
3. `qdbus org.kde.KWin /KWin reconfigure` — cleared replication state but position error persisted
4. Deleted `~/.local/share/kscreen/control/configs/` — no effect (state is in KWin runtime)
5. Killed `kscreen_backend_launcher` and relaunched — no effect
6. `kscreen-doctor --dpms on` — cleared replication source entries, but outputs stayed disabled
7. Stopped `sunshine-vmon.service`, killed `krfb-virtualmonitor` — left only DP-1, which then got `driver rejected` error from NVIDIA

### Status
Unresolved at time of writing. Investigation interrupted by user.

### Likely Cause
Exclusive mode disabling DP-1 via `kscreen-doctor output.DP-1.disable` leaves the NVIDIA KMS driver in a state where re-enabling the output requires a specific sequence that kscreen-doctor alone cannot produce after a session disruption. The circular replication (both outputs with `replication source: 2`) was a secondary symptom introduced by KDE's kscreen config restore logic running against the partially-disabled layout.

### Prevention
The `ExecStopPost` drop-in (`vmon-recovery.conf`) is supposed to run `sunshine-stop-vmon.sh` on Sunshine crash/stop to restore DP-1 before services restart. If `stop-vmon.sh` itself is failing (as seen in the logs), DP-1 can be left disabled across a service restart, causing this chain.

Need to investigate why `sunshine-stop-vmon.sh` was already failing to re-enable DP-1 before the manual restart.
